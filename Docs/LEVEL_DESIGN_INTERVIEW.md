## 결정 로그

> 확정된 것만 여기 쌓는다. 각 항목은 **질문 / 답 / 이유 / 딸려오는 작업** 순.
> 라운드가 끝나면 `DESIGN.md` 결정 로그로 옮기고 `LEVEL_DESIGN.md`를 갱신한다.

### D-1. 벽은 마찰이 없다. 벽점프는 기본 이동이 아니라 **능력**이다.

**질문** 1-1. 벽에 닿았을 때 무슨 일이 일어나야 하는가.

**답** 마찰 0으로 벽에 안 붙게 한다. 벽점프는 나중에 제작으로 얻는 능력(`Capability`)으로 연다.

**이유**
- 지금 벽에 걸려 미끄러지는 건 아무도 정하지 않은 Unity 기본값(마찰 0.4)이 만든 사고다.
- 마찰을 0으로 두면 `ReachabilityAnalyzer`가 주장하는 "실제 물리를 그대로 시뮬레이션한다"가
  비로소 사실이 된다 — 시뮬과 게임이 같은 물리를 쓴다.
- 벽점프를 기본으로 넣으면 모든 방이 "벽 타면 갈 수 있는 곳"이 돼 지형 문법이 무너진다.
  능력으로 두면 게임 정체성(E + 글자 → 능력 → 관문)과도 맞물린다.

**딸려오는 작업**
1. `PhysicsMaterial2D`(friction 0, bounciness 0) 생성 → `Physics2DSettings.m_DefaultMaterial`에 지정.
   개별 콜라이더가 아니라 기본값에 걸어야 새로 만드는 오브젝트까지 자동으로 따른다.
2. 벽점프 능력은 추후: `Capability`에 값 추가 + `AnalyzerOptions`에 스위치
   (`AllowDash` 선례가 이미 있다).
3. **★ 제약**: 도달성 검증은 **능력이 없는 상태**를 기준으로 통과해야 한다.
   능력으로만 갈 수 있는 곳은 **보상**이지 통행로가 아니다
   (특수방 규칙 "보상은 선택, 통행은 보장"과 같은 원리).

### D-2. 이중점프도 기본이 아니라 **능력**이다.

**질문** 1-2. 이중점프를 넣을 것인가.

**답** 기본 이동에는 없다. 제작으로 얻는 능력(`Capability`)으로 연다. (벽점프와 같은 노선)

**이유**
- 기본 이동 어휘를 걷기/점프/대시로 좁게 유지해야 "저기는 갈 수 있나"가 한눈에 읽힌다.
- 이동 능력을 제작 대상으로 두면 성장감이 이동 자체에서 나온다 — 게임 정체성과 맞물린다.

**딸려오는 작업 / 파생 규칙**
- 이동 능력이 둘(벽점프·이중점프)이 되면서 **검증이 두 겹**이 된다:

  | 층위 | 기준 | 성격 |
  |---|---|---|
  | **통행** | 이동 능력 **0개** 상태로 문↔문이 통해야 한다 | 하드 불변식 (깨지면 클리어 불가) |
  | **보상** | 능력이 있으면 더 갈 수 있다 | 선택 (못 가도 방은 통과된다) |

- `AnalyzerOptions`에 능력 스위치를 추가하고, `RoomTemplateValidator`는
  **능력 0개 기준으로 통행을 검사**한다. 능력이 있어야 닿는 칸은 보상으로만 쓴다.

> ⚠ **대시는 예외다.** 대시는 능력이 아니라 기본 이동이고, 검증기도 `AllowDash = true`가
> 기본이라 "대시가 있어야 건너는 갭"을 통행로에 쓸 수 있다. 능력(벽점프·이중점프)과는
> 층위가 다르다는 것을 명시해 둔다.

### D-3. 공중 대시는 **착지할 때까지 1회**.

**질문** 1-3. 공중 대시를 어떻게 할 것인가.

**답** 공중에서는 1회만. 착지해야 다시 충전된다. (기존 쿨다운은 지상 연타 억제용으로 유지)

**이유**
- 지금도 체공 0.885초 / 쿨다운 0.8초라 사실상 점프당 1회지만, 그게 **시간**에 걸려 있어
  체공이 길어지는 상황(높은 곳에서 낙하, Tall 31칸 방)에서는 연속으로 쓸 수 있었다.
- 착지 기준으로 바꾸면 **"갭 하나당 대시 하나"가 보장**돼 지형 설계가 예측 가능해지고,
  도달성 시뮬도 "한 체공에 대시 1회"라는 단순한 모델이 된다.

**딸려오는 작업**
1. `PlayerController`: 착지 시 리셋되는 공중 대시 플래그 추가 (쿨다운과 **별개 조건**).
2. `ReachabilityAnalyzer`: 한 체공당 대시 1회 모델로 정리 — 시간 기반 쿨다운을 시뮬할 필요가 없어진다.
3. 갭 문법(6~7칸 = 대시 필요)은 그대로 유효하며, 이제 **보장된 규칙**이 된다.

### D-4. 점프 무게감은 **Play로 판단한다** (보류)

**질문** 1-4. 점프 3.51타일 / 정점 0.5초라는 무게감이 맞는가.

**답** 지금 정하지 않는다. **D-1(마찰 0)·D-3(공중 대시 1회)을 적용한 뒤** 새 지형에서
직접 뛰어보고 정한다.

**이유**
- 손맛은 표로 결정할 수 없다.
- 특히 마찰 0.4가 사라지면 체감이 지금과 달라진다 — 현재 값을 지금 판단하면 금방 무효가 된다.

**보류 중 유효한 것**: 현행 값(3.51타일)이 잠정 기준이며, 문법 수치·템플릿 10장·테스트가
전부 여기 맞춰져 있다. 바꾸기로 하면 그 전부가 따라온다.

### D-5. 적은 지형을 따라온다 — **점프/낙하를 준다**.

**질문** 2-1. 플레이어가 발판 위로 도망갔을 때 어떻게 돼야 하는가.

**답** 근접 적에게 점프와 낙하 추적을 준다. 발판을 따라 올라오고 구덩이를 넘는다.

**이유**
- 지금 적은 수평 추격만 해서, 발판 위가 완전한 안전지대가 된다. 특히 북문 사다리를
  전 방에 넣은 뒤로는 **모든 방에 도피처가 생겼다.**
- 전투가 지형과 엮여야 방 설계가 의미를 갖는다.

**딸려오는 작업 (큰 변경)**
1. **`EnemyPerception`에 지형 정보가 들어가야 한다.** 지금은 `SelfX`/`TargetX`/`DistanceToTarget`뿐이라
   **AI가 지형을 전혀 못 본다.** 최소한 "앞에 낭떠러지가 있는가", "타깃이 위에 있는가",
   "점프하면 닿는가"가 필요하다.
2. `EnemyAI`는 순수 로직으로 유지한다 — MonoBehaviour(`EnemyBase`)가 지형을 탐침해
   `EnemyPerception`에 담아주고, 판단은 계속 순수 쪽에서 한다(EditMode 테스트 유지).
3. `EnemyState`에 점프/공중 상태를 추가할지, 기존 Chase 안에서 처리할지 결정 필요.

**폐기되는 규칙**
- `LEVEL_DESIGN.md`의 *"발판 위에 안전지대를 만들지 마라 / 모든 발판은 바닥과 3타일 이내"* —
  AI 한계를 지형으로 떠받치던 규칙이라 더 이상 필요 없다. **지형 설계가 자유로워진다.**

**새로 생기는 규칙**
- 적의 점프 높이가 **지형 문법의 두 번째 축**이 된다. 플레이어 점프(3.51타일)와
  적 점프가 다르면, 그 차이가 곧 "적이 못 오는 높이"를 정의한다 → 2-2에서 결정.

### D-6. 적 점프 높이는 **아키타입마다 다르다**.

**질문** 2-2. 적의 점프 높이를 플레이어(3.51타일)와 어떻게 놓을 것인가.

**답** 아키타입/개체별로 다르게 둔다. 예: 그런트는 높이, 브루트는 낮게, 아처는 안 뛰고 사격.

**이유**
- 발판 높이가 **"어떤 적이 여기까지 오는가"를 정하는 설계 도구**가 된다.
  같은 지형에 어떤 적을 놓느냐로 난이도를 조절할 수 있다.
- 전부 같은 높이면 지형으로 전술적 우위를 만들 수 없어 전투가 평면적이 된다.

**딸려오는 작업**
1. 점프 높이는 `EnemyArchetype` enum이 아니라 **`EnemyBase`의 직렬화 필드**로 둔다
   (`_moveSpeed`·`_attackRange`와 같은 층위). 아키타입은 행동 패턴, 점프 높이는 스탯이다.
   프리팹 4종(Grunt/Archer/Brute/Boss)이 값만 달리한다.
2. `EnemyPrefabDataTests`에 점프 높이 검증을 넣을지 검토 (프리팹 직렬화 값 회귀 방지).
3. **레벨 문법이 한 줄이 아니게 된다.** 지금까지는 "플레이어 3.51타일" 하나였는데,
   이제 적 종류별 표가 붙는다:

   | 발판 높이 | 올라오는 적 |
   |---|---|
   | 낮음 | 전부 |
   | 중간 | 그런트만 |
   | 높음 | 없음 (아처 사격만 닿음) |

4. 뷰어(`Room Template Viewer`)에 **적 도달성 오버레이**를 추가하면 저작 중에 바로 보인다
   — 플레이어 도달성과 별개 레이어. (`ReachabilityAnalyzer`가 점프력을 파라미터로 받으므로
   같은 코드에 다른 수치만 넣으면 된다)

### D-7. 위험 지형 인지도 **아키타입마다 다르다** — 유인 플레이가 성립한다.

**질문** 2-3. 추격하던 적이 가시·구덩이 앞에 오면 어떻게 되는가.

**답** 아키타입마다 다르게. 영리한 적은 난간 앞에서 멈추고, 무단한 적은 그대로 뛰어든다.

**이유**
- 적 종류가 곧 방 설계의 어휘가 된다(D-6과 같은 결의). 유인 플레이가 통하는 방과
  안 통하는 방이 갈려서, 같은 지형도 배치에 따라 다른 문제가 된다.
- `DESIGN.md`의 "전투 퍼즐 = 환경 활용"이 실제 메커니즘으로 성립한다.

**딸려오는 작업**
1. `EnemyPerception`에 "앞이 위험/낭떠러지인가" 탐침 추가 (D-5의 지형 인지와 같은 통로).
2. 위험 회피 여부를 `EnemyBase` 직렬화 필드로 (점프 높이와 같은 층위).

**⚠ 첫 번째 불변식과 충돌 가능 — 반드시 처리해야 함**

`LootDistribution`이 방의 층 예산 글자를 적들에게 나눠주고, **전멸하면 방 몫 전량**이
보장되는 구조다(재료 보장 불변식). 그런데 적이 구덩이에 빠져 죽으면:

- 드랍이 구덩이 안에 떨어져 **주울 수 없게 된다** → 보장이 깨진다
- 적이 구덩이에서 죽긴 하는가? 플레이어는 "15뎀 + 입구 복귀"인데 적의 규칙은 미정

**처리 방향(미결)**: 위험 지형에서 죽은 적의 드랍은 안전한 칸으로 튕겨 나오게 하거나,
방 클리어 시 미획득 드랍을 입구로 회수한다. 구현 시 결정.

### D-8. 보스 방은 **보스마다 전용으로 짠다**.

**질문** 2-4. 보스 방 지형 원칙 — 모델이 써놓은 *"발판은 최소한만, 공중에 붙어 무한 회피 금지"* 를 어떻게 할 것인가.

**답** 그 지침은 폐기한다. 보스 방은 일반 규칙을 따르지 않고 **보스의 패턴에 맞춰 한 장씩 설계**한다.
넘는 보스에게는 기둥을, 돌진하는 보스에게는 넘어질 장애물을 준다.

**이유**
- 원래 지침은 "적이 발판을 못 따라온다"는 AI 한계에서 나온 방어적 규칙이었다.
  D-5로 적이 지형을 따라오게 되면서 **전제 자체가 사라졌다.**
- 보스전은 층의 마지막이자 가장 기억에 남아야 하는 구간이라, 절차적 조합보다 손 설계가 맞다.

**딸려오는 작업**
1. 보스 템플릿을 **보스 정체성에 묶는다.** 지금은 `RoomTemplateLibrary`가 `RoomType → 템플릿`
   한 겹이라, 보스별 매핑(보스 프리팹 ↔ 전용 템플릿)이 필요하다.
2. 현재 보스는 1종(강화 브루트)뿐이므로 당장은 `Boss_Wide_01` 한 장으로 충분하다 —
   보스가 늘어날 때 매핑을 도입한다.
3. **미결**: 보스 방에 북문 사다리를 남길 것인가, 아니면 **보스 방은 세로 연결을 금지**하고
   사다리를 빼서 공간을 되찾을 것인가. (전용 설계라면 방마다 판단해도 된다)

### D-9. 세로 이동은 **지형으로 올라간다**. 문은 그 지형이 닿는 곳에 놓는다.

**질문** 3-1/3-2. 천장의 북문까지 올라가는 길을 어떻게 만들 것인가. 지형인가, 플레이어가 가져오는 장치인가.

**답** 지형으로 그린다. 전용 사다리 오브젝트도, 로프 능력도 필요 없다.
대신 **북문을 천장 정중앙에 고정하지 않고, 지형이 자연스럽게 올라간 끝에 놓는다.**

> 논의 중 방향이 한 번 바뀌었다. 처음엔 "사다리·밧줄 같은 전용 장치"로 갔다가,
> 문 위치를 옮길 수 있다는 걸 확인하고 **지형만으로 해결**하는 쪽으로 정리됐다.

**핵심 발견 — 문 위치는 이미 자유였다**

`RoomTemplateParser.RegisterDoor`는 문의 **방향을 "어느 변에 있느냐"로만** 정한다:

```csharp
if (cell.y == height - 1) dir = Direction.North;   // 천장 행이면 북문 — 열은 무관
```

`RoomManager.DoorTilePos`도 템플릿 좌표를 우선해서 읽는다(가운데 고정은 폴백일 뿐).
**10장이 전부 정중앙에 있던 건 모델이 그렇게 그려서였고, 코드 제약이 아니었다.**
문은 여전히 테두리 위에 있으므로 **사각형 방 규칙은 깨지지 않는다.**

**관계가 뒤집힌다**

| | 전 | 후 |
|---|---|---|
| 문 | 천장 정중앙 고정 | 지형이 올라간 끝 (천장 어느 열이든) |
| 지형 | 문까지 억지로 올라가야 함 | 자연스럽게 그린다 |
| 결과 | 방 한복판에 수직 기둥 | 계단식 지형 + 가운데가 비어 전투/퍼즐 공간이 산다 |

```
#####################D####     ← 지형이 올라간 끝에 북문
#..................---...#
#...............---......#
#............---.........#
#.........---............#
D....p...................D
============D=============
```

**딸려오는 작업**
1. **템플릿 10장 재작업**: 2026-09-06에 넣은 정중앙 발판 4단을 걷어내고,
   계단식 지형 + 북문 위치 이동으로 다시 그린다.
2. 코드 변경은 **없다.** 검증기(퇴장 지점)와 파서가 이미 이 구조를 지원한다.
3. 로프는 Phase 3에 별개 물리 상호작용으로 남긴다 — 세로 통행 수단이 아니라 퍼즐 도구.

### D-10. 세로 문의 열은 **맞추지 않는다** — 문은 포털이다.

**질문** 3-3. 위아래로 이어지는 방끼리 문 열이 안 맞는 문제.

### D-11. 크기는 **템플릿이 정한다**. 방 유형과 크기는 독립적인 두 축이다.

**질문** 4-1. "방 하나 = 한 화면"이 맞는 문법인가.

**답** 확률로 굴리지도, 유형이 강제하지도 않는다. **유형마다 여러 크기의 템플릿이 존재**하고,
템플릿을 고르면 크기가 따라온다. 퍼즐도 Wide일 수 있고 전투도 Tall일 수 있다.

**이유**
- 유형(용도)과 크기(공간)는 다른 축이다. 묶으면 "전투는 항상 넓다" 같은 단조로움이 생긴다.
- 저작자가 방을 그릴 때 크기를 자유롭게 고르는 게 자연스럽다 — 그린 결과가 곧 그 방의 크기다.

**⚠ 현재 구조가 거꾸로다 (실패 모드 발견)**

```csharp
RoomTemplateLibrary.Pick(RoomType type, RoomSizeClass sizeClass, int seed)  // 크기가 입력 필터
```

`DungeonGenerator.AssignRoomSizes`가 24% 확률로 크기를 **먼저 굴리고**, 라이브러리가 그 크기의
템플릿을 찾는다. 그런데 **현재 템플릿은 보스(Wide)를 빼면 전부 Small**이라,
Wide/Tall이 굴려지면 매칭에 실패해 **절차적 빈 상자**로 떨어진다.
"방이 휑하다"의 또 다른 원인이다.

**딸려오는 작업**
1. `Pick(type, seed)` — 크기 필터 제거. 유형에 맞는 템플릿 중에서 고른다.
2. `Room.SizeClass`는 **고른 템플릿에서 파생**된다. `AssignRoomSizes`와 `LargeRoomChance`(24%)는 삭제.
3. "보스는 항상 Wide", "시작 방은 항상 Small"도 코드가 아니라 **데이터**가 된다
   (보스 템플릿을 Wide로 그리면 그만).
4. `DungeonGeneratorSizeTests` 재작성.
5. `RoomManager`는 이미 `_roomWidth = _resolved?.Width ?? dim.Width`로 **템플릿 크기를 우선**한다 —
   렌더 쪽은 이미 이 방향이라 바꿀 게 적다.
6. **저작 부담**: 유형마다 크기별 템플릿이 있어야 다양성이 나온다. 지금은 유형당 1~3장, 거의 Small.

### D-12. 구덩이는 **순간이동 장치가 아니라 지형**이다. 빠지면 걸어 나온다.

**질문** 5-1. 지형이 플레이어를 죽일 수 있어야 하는가.

**답** 죽이지 않는다. 그리고 **입구 복귀(순간이동)를 없앤다.** 구덩이에는 바닥이 있고,
빠지면 피해를 입되 거기서 다시 걸어 올라온다.

**이유**
- 런이 1시간 이상이라 지형 실수 한 번으로 날아가면 가혹하다.
- 입구 복귀는 물리적으로 말이 안 되는 순간이동이었다. 바닥을 두면 방이 **입체적으로** 변하고
  아래 공간이 설계 대상이 된다.

**딸려오는 작업**
1. `RoomHazard`에서 구덩이의 위치 복귀 제거 — 피해만 준다. `RoomManager._entryPoint` 복귀 경로도 정리.
2. **구덩이의 정체가 바뀐다.** "빠지는 구멍"이 아니라 **움푹 파인 지형 + 바닥의 피해 타일**이다.
   그러면 `^`(가시)와 `~`(구덩이)의 차이는 **피해량뿐**이 된다 — 둘을 합칠지 검토할 여지가 생긴다.
3. **★ 새 불변식**: *구덩이에 빠져도 방을 계속 돌 수 있어야 한다.*
   `ReachabilityAnalyzer`는 지금 위험 칸을 "지나갈 수 없는 칸"으로 치는데,
   구덩이는 **들어갈 수 있고 나올 수 있어야 하는 칸**이 된다. 판정을 나눠야 한다:

   | | 통과 | 체류 |
   |---|---|---|
   | 가시 `^` | 지나갈 수 있음(피해) | 서면 안 됨 |
   | 구덩이 바닥 `~` | 지나갈 수 있음(피해) | **여기서 올라올 수 있어야 함** |

4. 못 올라오는 구덩이는 방을 가두는 함정이 되므로 **검증기가 반드시 잡아야 한다.**

## 라운드 1 — 이동 능력

**모든 지형 수치가 여기서 파생된다.** 여기가 바뀌면 단차/갭/통로 문법,
EditMode 테스트, 템플릿 10장이 전부 따라온다.

### 현재 상태 (누가 정했나)

| 항목 | 값 | 정한 사람 |
|---|---|---|
| 중력 스케일 | 2.85 → 점프 3.51타일, 정점 0.5초 | 모델 |
| 낙하 배수 | 1.7 (낙하 0.38초, 상승보다 빠름) | 모델 |
| 이동 속도 | 7 (점프 수평거리 6.19타일) | 모델 |
| 대시 | 3타일 / 쿨다운 0.8초, 대시 중 수직속도 0 | 모델 |
| 코요테 타임 | 0.10초 | 모델 |
| 점프 버퍼 | 0.12초 | 모델 |
| 가변 점프 | 있음 (일찍 떼면 ~1.4타일) | 모델 |
| 벽점프 / 이중점프 | 없음 | 모델 |
| **벽 마찰** | **0.4 (Unity 기본값)** | **아무도** |

### 확인된 문제

- 프로젝트에 `PhysicsMaterial2D`가 **하나도 없다**. 씬의 모든 콜라이더가
  `m_Material: {fileID: 0}`이고 `Physics2DSettings.m_DefaultMaterial`도 비어 있어
  Unity 내장 기본값(마찰 0.4)이 적용된다. 공중에서 벽 쪽으로 밀면 걸려서 미끄러진다.
- `ReachabilityAnalyzer`는 "실제 물리를 그대로 시뮬레이션한다"고 주장하지만
  `AnalyzerOptions`·`PlatformerMetrics` 어디에도 마찰이 없다.
  **시뮬레이터는 마찰 0인 게임을 검증하고, 실제 게임은 마찰 0.4로 돌아간다.**

### 질문 목록

- [x] 1-1. 벽에 붙는 것을 없앨 것인가 → **D-1** (마찰 0 + 벽점프는 능력)
- [x] 1-2. 이중점프를 넣을 것인가 → **D-2** (능력으로)
- [x] 1-3. 대시는 공중에서 되는가 → **D-3** (공중 1회, 착지 충전 / 수직·대각 대시 없음)
- [x] 1-4. 점프 무게감 → **D-4** (보류 — D-1·D-3 적용 후 Play로 판단)

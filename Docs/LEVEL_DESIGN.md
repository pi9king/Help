## 1. 플레이어가 할 수 있는 것 (문법의 근거)

| 항목 | 값 | 비고 |
|---|---|---|
| 점프 높이 | **3.51 타일** | JumpForce 14, gravityScale 2.85 |
| 정점까지 | 0.50 초 | 낙하는 0.38초(중력 1.7배) — 상승보다 빠르다 |
| 점프 수평거리 | 6.19 타일 | 체공 0.885초 × 이동속도 7 |
| 대시 | 3.0 타일 / 쿨다운 0.8초 | 대시 중 수직속도가 0이 된다 |
| 몸 크기 | 폭 0.5 · 높이 1.0 타일 | 판정은 0.6 × 1.2로 **보수적**으로 본다 |

보조 기능: **코요테 타임 0.10초**(난간에서 떨어진 직후에도 점프), **점프 버퍼 0.12초**
(착지 직전 입력 보존), **가변 점프**(버튼을 일찍 떼면 ~1.4타일). 벽점프·이중점프는 없다.

## 2. 지형 문법 (이 표가 전부다)

### 단차 — 위로 올라가기

| 높이 | 의미 |
|---|---|
| 1~3 타일 | **오를 수 있다.** 자유롭게 쓴다 |
| **4 타일 이상** | **벽이다.** 발판을 대주지 않으면 못 올라간다 |

> 바닥(y=0) 위에 놓는 발판은 **y=3 이하**여야 한다. (발 위치가 y=4 = 단차 3)
> y=4에 놓으면 발 위치 y=5 = 단차 4 → 아무도 못 올라간다. 가장 흔한 실수다.

### 갭 — 옆으로 건너기

| 폭 | 의미 | 용도 |
|---|---|---|
| 1~3 칸 | 편하게 건넌다 | 일반 지형 |
| 4~5 칸 | 건널 수 있지만 타이밍이 필요 | 2~3층 긴장 구간 |
| 6~7 칸 | **대시가 있어야 건넌다** | 선택적 보상 잠그기 |
| **8 칸 이상** | 아무 조작으로도 못 건넌다 | 경로 차단(다른 길을 반드시 줄 것) |

`PlatformerMetrics.CanClearGap`은 이보다 두 칸 보수적인 **설계 권장치**(대시 없이 3, 대시 5)를
돌려준다. 위 표는 **물리 한계**다. 둘의 차이가 플레이어의 여유분이다.

### 통로 높이

**세로 2칸 이상.** 웅크리기가 없어서 1칸 통로는 몸이 안 들어간다.

### 위험 지형

| 문자 | 효과 |
|---|---|
| `^` 가시 | 밟으면 12 피해. 도달성 계산에서 **지나갈 수 없는 칸**으로 친다 |
| `~` 구덩이 | 빠지면 15 피해 + 방 입구로 되돌아간다 |

둘 다 `RoomHazard`가 실제로 판정한다 — 문자만 찍어두면 되는 장식이 아니다.

## 3. 방 크기

| 등급 | 크기 | 카메라 | 쓰임 |
|---|---|---|---|
| Small | 25 × 15 | **고정**(방 중앙) | 기본. 한 화면에 다 보인다 |
| Wide | 51 × 15 | 좌우 추적 | 보스, 넓은 전투 |
| Tall | 25 × 31 | 상하 추적 | 수직 퍼즐, 탐험 |

던전 생성기가 배정한다: 보스는 항상 Wide, 시작 방은 항상 Small,
나머지는 24% 확률로 Wide/Tall(`DungeonGenerator.LargeRoomChance`).

**기본은 Small이다.** 방 하나가 한 화면에 다 보이는 것이 이 게임의 기본 문법이고
(퍼즐 방은 특히 그래야 푼다), 큰 방은 예외로 쓴다.

## 4. 아스키 문자표

### 지형
```
#  벽             =  지면
-  일방통행 발판 (아래에서 통과)
.  빈 공간        ^  가시         ~  구덩이
D  문 (4방향 모두 예약 — 연결 없는 쪽은 자동으로 벽이 된다)
```

### 마커 — 지형이 아니라 "여기에 스폰"
```
p  플레이어 시작   e  일반 적      E  원거리/엘리트 적
x  퍼즐 장애물     l  루팅         c  상자/제작대      b  보스
```

### 확률 문자 — 템플릿 하나를 여러 방으로
```
?  50% 발판, 아니면 빈칸
%  50% 적,   아니면 빈칸
```

확률 칸은 **양극단(전부 채움 / 전부 비움) 모두에서 방이 돌 수 있어야** 한다.
검증 테스트가 두 경우를 다 본다. 즉 확률 칸을 유일한 통로로 쓰면 안 된다.

### ★ 세로 문에는 반드시 올라갈 길을 준다

`D`는 4방향 모두 예약되고, 던전이 어느 쪽을 연결할지는 방마다 다르다. 그래서
**천장의 북문에도 언제나 올라갈 수 있어야 한다.**

문 칸은 `Wall`로 저장된다(셸에 구멍을 내지 않는다). 그래서 문 **바로 아래** 칸에 서면
머리가 문에 걸린다 — 실제로 서야 하는 자리는 **문에서 두 칸 아래**다.
15칸 방 기준 바닥에서 거기까지 단차 3 이하로 이으면 발판 4단이 나온다:

```
row 0   ############D############   ← 북문
row 3   #..........---..........#   ← 여기 서서 나간다
row 5   #..........---..........#
row 8   #..........---..........#
row 11  #..........---..........#
row 14  ============D============   ← 바닥
```

이걸 빠뜨리면 **떨어져 들어올 수는 있는데 나갈 수 없는 방**이 된다.
`RoomTemplateValidator`가 진입 지점(낙하 허용)과 퇴장 지점(낙하 불허)을 따로 잡아
`DoorAccessValidationTests`·`RoomTemplateReachabilityTests`에서 잡아낸다.

### 그 밖의 규칙
- 첫 줄이 방 **천장**, 마지막 줄이 **바닥**
- `;`로 시작하는 줄은 주석
- 모든 줄의 길이가 같아야 하고, 크기가 위 3등급 중 하나와 정확히 맞아야 한다
- 문은 반드시 4개(각 방향 하나씩), 테두리 위에

## 5. 방 유형별 설계 원칙

### Combat
- **근접 적이 못 오는 곳을 만들지 마라.** 적 AI는 **수평 추격만** 한다(점프·시야 없음).
  플레이어가 발판 위에 올라가 무한히 안전하면 전투가 성립하지 않는다.
  → 모든 발판은 바닥과 3타일 이내로 이어 두고, 발판 위에서도 아래 적에게 맞을 여지를 둔다.
- **궁수(Archer)는 고지대에.** aggro 8 / standoff 4 / 사거리 6이라 높은 곳에서 사선을 준다.
  플레이어가 "저 위를 먼저 정리할지, 아래를 뚫을지" 고르게 된다.
- 브루트(느리고 아프다)는 좁은 통로에, 그런트는 열린 바닥에.

### EnvironmentPuzzle / PurePuzzle
- `x` 마커를 **출구로 가는 길 위에** 둔다. 옆길로 우회되면 퍼즐이 아니다.
- 지형은 통과 가능하게 그린다 — 막는 건 장애물(콘텐츠 레이어)이지 지형이 아니다.
  검증기는 지형만 보므로, 지형까지 막으면 "이 방은 깨졌다"고 잡힌다.
- PurePuzzle은 Tall 방에서 수직으로 올라가는 구성이 잘 맞는다.

### CombatPuzzle
- `RoomPuzzle`이 출구를 잠그므로 **완전한 안전지대를 두지 않는다.** 숨어서 기다리면 끝나는 방이 된다.

### Treasure / Shop
- 전투 없음. 보상을 3타일 발판 위에 둬서 "올라가서 얻는" 동작을 만든다.

### Secret
- 보상을 **6칸 갭 뒤**(대시 필요)에 두되, **바닥은 끊지 않는다.**
  못 건너도 방은 통과할 수 있어야 한다.
  > ※ "보상은 선택, 통행은 보장"이라는 표현은 **모델이 쓴 문장**이며 사용자 결정이 아니다.
  > 관련된 실제 결정은 `DESIGN.md` 2026-08-14의 특수방 항목("클리어에 필요한 것은 절대 넣지 않는다")이고,
  > 그건 Secret 방에 국한된 규칙이다.

### Boss
- Wide 고정. 보스 사거리 2.2 / aggro 9를 고려해 도망칠 가로 공간을 넓게.
- 발판은 최소한만. 공중에 붙어서 무한 회피하는 방이 되면 안 된다.

### Tutorial
- 시작 방. 가시·구덩이 없음, 지형 평탄. `Docs/KEY_TUTORIAL.md`의 수직 슬라이스
  (줍기 → 제작 → 장착 → 문 열기)를 지형이 방해하지 않게 한다.

## 7. 작업 흐름

1. **그린다** — `Assets/Rooms/{RoomType}_{SizeClass}_{NN}.txt`
   손으로 25×15를 타이핑하면 줄 길이가 어긋나기 쉽다. `Tools/gen_rooms.py`처럼
   빈 방에서 시작해 스탬프로 찍으면 길이가 항상 맞는다.
2. **본다** — Help ▸ Level ▸ Room Template Viewer
   도달성 오버레이(초록=갈 수 있음, 빨강=못 감), 칸을 클릭하면 거기서 갈 수 있는 범위,
   확률 시드 슬라이더로 변형 확인.
3. **검증한다** — EditMode 테스트
   ```bash
   "$UNITY" -batchmode -nographics -runTests -testPlatform EditMode -projectPath . -testResults r.xml
   ```
   `RoomTemplateReachabilityTests`가 `Assets/Rooms/*.txt` **전량**을 확률 양극단으로 검사한다.
4. **연결한다** — Help ▸ Setup ▸ Setup Room Templates
   파일명에서 방 유형을 읽어 `RoomTemplateLibrary.asset`에 등록하고 씬에 물린다.
5. **돌아본다** — Play. 검증은 "막히지 않았다"만 보장한다. "재미있는가"는 사람이 본다.

## 8. 왜 자동 검증이 필요한가

방 하나에 발판을 놓기 시작하면 **템플릿 30개 중 반드시 하나는 막힌다.**
눈으로는 안 잡힌다 — "저기 올라갈 수 있나?"는 점프 높이 3.51타일과 갭 폭을
머릿속에서 계산해야 하는 문제이기 때문이다.

`ReachabilityAnalyzer`는 근사식이 아니라 **실제 물리를 그대로 시뮬레이션**한다.
`PlayerController`와 같은 중력·점프력·대시 값을 쓰므로, 물리를 바꾸면 판정도 따라온다.
판정은 항상 보수적인 쪽으로 기운다 — *갈 수 있는데 못 간다*고 하면 방이 조금 답답할 뿐이지만,
*못 가는데 갈 수 있다*고 하면 클리어 불가능한 방이 배포된다.

이것은 `FloorValidator`의 **재료 보장 불변식**에 이어지는 두 번째 불변식이다:

> **어느 문으로 들어오든, 다른 모든 문과 모든 스폰 지점에 갈 수 있어야 한다.**

둘이 합쳐져야 "생성된 던전은 반드시 클리어 가능하다"가 성립한다.

## 출발점과 결정

기존 Idle·걷기·공격은 바라보는 방향이 모호하고, 몸통·팔·발이 따로 움직이는 듯 보였다.
네 방향 모두 살펴보기로 했고, Idle 한 장으로 결정하기 어려워 A/B의 Idle·걷기·공격
프로토타입을 함께 비교했다.

| 시안 | 특징 | 판단 |
|---|---|---|
| A | 기존 E 실루엣을 더 가깝게 유지 | 색상과 이전 모습의 비교 기준으로 보관 |
| B | Down을 정면으로 읽기 쉽게 만들고 팔·발·몸통의 방향을 맞춤 | 사용자가 방향 설계로 선택. 움직임은 추가 수정 필요 |

B 선택은 움직임의 완성 판정이 아니다. 사용자는 걷기가 조금 이상하지만 방향 자체는 B가
맞는다고 판단했다. 명세서의 방향·정면 자세 규칙과 게임용 8개 시트를 B 기준으로 갱신했다.

## 색상 수정 경과

1. B 적용 후 사용자가 이전보다 색감이 많이 달라졌다고 지적했다.
2. 첫 수정은 A/B의 재질별 대표색 차이를 B에 더하는 방식이었다. 픽셀 값은 변했지만
   화면에서 거의 구분되지 않아 사용자가 다시 수정을 요청했다. **이 방식은 폐기했다.**
3. 두 번째 방식은 `Archive/BeforeB/E_Master.png`에서 32색 팔레트를 추출해 가장 가까운 색으로
   매핑했다. 사용자가 **"여전히 색감이 많이 다르다"**고 지적해 **폐기했다** (2026-10-05).
   원인: 가장 가까운 색 매핑은 B 자체의 밝기 분포를 그대로 남긴다. 그래서 갑옷은 거의 검정,
   망토는 밝은 주홍으로 남았다.
4. **현재 방식 — 재질별 히스토그램 매칭** (`Tools/e_color_transfer.py`).
   OkLCh 색상각으로 중립(갑옷)·빨강(망토)·금장·청록(룬)을 나누고, B 픽셀이 자기 재질 안에서
   n번째 밝기 백분위면 A Master 같은 재질의 같은 백분위 색을 준 뒤 A의 실제 색으로 스냅한다.
   시트마다 따로 매칭해서 컨셉별 톤 차이(Walk 망토가 더 주황인 것 등)도 같은 A 램프로 모인다.
   망토/금장 경계는 모든 시트 색상각 히스토그램의 골짜기인 **33°**다.
5. 비교 이미지(`A_B_restored_comparison.png` 등)와 3번 방식 직전 백업(`Archive/BeforePaletteRollbackB/`)은
   2026-10-06 정리에서 삭제했다. 확인은 이미지가 아니라 미리보기 씬으로 한다(사용자 결정).

### 자동으로 못 고친 것 — 컨셉 그림 자체의 문제

크기 통일을 선택한 결과로 생기거나, 원본 컨셉에 이미 있는 것들이다. 고치려면 해당 프레임을 다시
그리거나 다시 생성해야 한다. **어떻게 할지는 정해지지 않았다.**

- Walk·Attack·Hit의 넓은 망토 끝, Walk Down 짝수 프레임의 검이 셀 가장자리에서 잘린다 (크기 통일의 대가).
- Walk Up f4~f6에서 검이 보이지 않는다. f1~f3에는 있다.
- Walk Down의 E 몸통이 Idle Down보다 옆으로 넓다 (키는 같음). 컨셉 비율 차이다.
- Attack Left·Right f4(찌르기)에서 E 글자가 회색 덩어리처럼 뭉개진다.
- Idle은 4프레임이 같은 그림이다 (미세 동작 없음, 기존 기록대로).

사용자 지적: *"좌우 걷기가 짤리는 느낌"*, *"공격을 더 부드럽게"*, *"Down 공격 때 발이 늘어나는 게 어색"*.

**모델이 정한 값 — 사용자 확인 필요** (인스펙터나 상수에서 조정):
- 예비동작 구간 앞 40%는 예비동작, 나머지는 치켜듦. 판정 구간 앞 60%는 타격, 나머지는 팔로스루 (`AttackFrameTiming`)
- 위아래 공격 이동 비율 0.35 (`ECharacterAnimator._lungeVerticalScale`)
- Walk는 크기 통일 결정에 따라 뒤로 날리는 망토가 여전히 셀 가장자리에서 잘린다 (Left 최대 20px)

**검사 기준 변경:** `Tools/Test-E-SpriteAlignment.ps1`의 "발 중심이 피벗 ±2px" 검사를
**"E 윗막대 중심이 같은 방향 Idle ±1.5px"**로 바꿨다. 예전 기준은 위 걷기 흔들림 버그를 만든 바로 그

## 방향별 애니메이션 속도 점검 (2026-10-05)

사용자 지적: *"왼쪽 공격과 오른쪽 공격의 시간이 다르고, 왼쪽 걷기와 오른쪽 걷기도 다르다."*

**확인한 사실 (방향별 차이 없음)**
- 클립 18개: 같은 동작이면 방향별로 샘플레이트·키 수·길이가 같다 (Walk 11fps 6장, Attack 12fps, Hit 11fps, Idle 7fps)
- 컨트롤러: 상태 속도 전부 1, 전환 없음, 미러 없음
- 각 클립은 자기 방향 행의 칸을 순서대로 참조한다 (시트 메타의 rect로 확인)
- 공격 시간: 판정(`PlayerController._attackTimer`)과 그림(`AttackFrameTiming`) 모두 무기 타이밍만 쓴다. 방향은 관여하지 않는다
- `ECharacterFacing.From`은 좌우 대칭이다
- 그려진 공격 리듬도 Left·Right가 같다 (f3 치켜듦 96~99°, f4 베기, f5 팔로스루)

**고친 것 — 걷기 루프 멈칫 (네 방향 공통)**
`BuildEAnimationPreview.SetFrames`가 루프 클립 끝에도 첫 프레임 키를 하나 더 붙였다. 스프라이트 커브는
마지막 키를 한 프레임 동안 보여 주므로, 루프 경계에서 f1이 두 번 연속(0.18초) 나왔다. 루프 클립은 유지 키를
빼도록 코드를 고치고, 이미 만들어진 Walk·Idle 클립 8개도 같이 고쳤다 (Walk 0.636→0.545초).

**남은 원인 후보 (확인 필요)**
- **걷기 방향이 이동이 아니라 마우스 조준을 따른다.** 마우스가 오른쪽에 있으면 왼쪽으로 걸을 때도
  Walk_Right가 재생된다 (뒤로 걷기). 이동 방향을 따르게 할지는 #8 조준 결정과 엮인 설계 문제다.
- 컨셉의 걸음 리듬이 방향마다 다르게 그려져 있다. 보폭이 가장 넓은 프레임이 Left는 f1·f6, Right는 f6·f1·f2에 있다.

## E 막대 길이 · 동작별 몸 비율 (2026-10-05)

**사용자 결정**
- *"E의 위와 아래 길이가 다르다"* → 확인 질문 후 **아랫막대를 윗막대 길이로 늘린다.**
  (Idle Down 윗막대 x17~47 = 31px, 아랫막대 x19~44 = 26px였다.)
- *"Idle→Walk 때 눌리는 느낌"* → 몸 비율의 기준은 **Idle**로 한다.

**측정 — 동작마다 E 비율이 달랐다** (머리폭 / 몸통높이, 키 52px 기준)

| | Down | Left·Right |
|---|---|---|
| Idle | 32 / 40 | 20 / 36~38 |
| Walk | 34 / 38 (다리 +2px) | 28~30 / — |
| Attack | 33 / 39 | 26 / — |
| Hit | 37 / 41 | 29~30 / — |

**처리** (생성기에 포함)
- `place_sheet(..., idle=...)`: Walk·Attack·Hit를 고해상도 컨셉 단계에서 Idle 비율로 다시 맞춘다. 머리폭은 가로
  배율로, Down·Up은 몸통과 다리를 각각 세로 배율로 맞춘다. 배율은 각 행의 첫 프레임에서 구해 행 전체에 같이
  적용하므로, 웅크리기 같은 그려진 움직임은 남는다.
  옆모습은 몸통이 팔만큼 좁아서 몸통·다리 경계를 잴 수 없다(측정이 검에 걸려 부츠가 늘어났다). 그래서
  **가로(머리폭)만** 맞춘다. 결과: 첫 프레임 머리폭과 몸통이 Idle과 ±1px.
- `match_down_bars`: 정면 프레임에서 아랫막대 양 끝 마감(왼쪽 3px, 오른쪽 4px)은 그대로 두고 가운데만 늘려
  윗막대 범위에 맞춘다. 적용: Idle·Master·Walk·Hit·Skill 전부, Attack f1~4·6, Equipment f1·2·4~6, Death f1~3.
  막대가 무기나 망토에 가려졌거나 무너진 프레임은 자동으로 건너뛴다.
- 옆모습 Walk·Attack·Hit는 머리가 좁아지면서 몸 전체(망토·검 포함)가 가로로 약 0.7배 좁아졌다.

## 정면·뒷모습 걷기 재구성 (2026-10-05)

사용자 지적: *"Walk 때 E 하단 막대 그래픽이 너무 깨진다"*, *"Up 걷기 프레임이 Down과 다르다"*.

- **원인 1:** Walk Down 컨셉은 프레임마다 E 몸통을 다시 그렸다. 거기에 비율 맞춤과 막대 늘리기가 겹치면서
  프레임마다 막대가 다르게 일그러졌다. 검 손이 막대에 붙어 있어 막대 범위 판정도 틀렸다.
- **원인 2:** 들린 발이 Down은 f1~f6에서 오른발·왼발을 번갈아 들지만, Up은 f4~f6에서 오른발만 들었다.
- **처리 (`compose_front_walks`):** Walk Down·Up = **Idle 상체(막대를 고친 E·팔·망토·검) + Idle 부츠**.
  부츠 움직임은 두 방향에 똑같이 적용한다.
- **뻣뻣함 보완 (사용자 요청):** 몸통 1px 오르내림을 넣었다. 컨셉 패턴(매 프레임 다른 발을 들어 한 바퀴에 세 걸음)에
  그대로 붙이면 초당 5.5회로 떨려서, 걸음 리듬도 함께 바꿨다:
  `WALK_STEPS` = 착지 → 오른발 4px 들기 → 2px 내리기 → 착지 → 왼발 4px → 2px. 발이 떠 있는 동안 상체(늘어진 검·망토 끝 포함)가
  1px 올라가고, 딛고 있는 다리는 1px 늘려 틈이 생기지 않게 한다. 값은 모델 제안이며 조정 가능하다.
- **대가:** 정면·뒷모습 걷기에서 팔과 망토는 움직이지 않는다 (원래 Walk Down도 팔 움직임이 작았다).
  옆모습 Walk는 그대로 컨셉 그림을 쓴다.

## 옆모습 걷기 재구성 (2026-10-05)

사용자 지적: *"좌우로 걸을 때 칼이 이상하게 흔들리고, 다리가 제자리에서 떴다 닿았다 하는 느낌. 좀 더 걷듯이."*

- **원인:** 옆모습 Walk는 컨셉 그림을 그대로 써서 칼 각도가 프레임마다 다르게 그려져 있었고, 발이 앞뒤로
  움직이지 않고 위아래로만 움직였다.
- **처리 (`compose_side_walks`):** Left·Right Walk = **Idle 옆모습 상체(칼 고정)** + Idle 다리 두 벌.
  가까운 다리는 원래 색, 먼 다리는 한 톤 어둡게(`FAR_LEG_SHADE` 0.72, A 팔레트로 스냅) 칠하고, 엉덩이를 축으로
  진자처럼 기울인다. 디딘 발은 뒤로 밀리고, 든 발은 앞으로 나간다(`SIDE_NEAR`/`SIDE_FAR`, 보폭 ±6px, 들림 3·2px).
  몸통 1px 오르내림은 정면·뒷모습과 같은 프레임이다.
- 옆모습에서는 몸통 측정이 팔 보호대에 걸려서, 다리는 바닥 위 10줄(`SIDE_LEG_ROWS`, 무릎 보석부터)로 고정했다.
- 보폭·들림·음영 값은 모델 제안이다. 옆에서 본 부츠가 16px로 길어 두 다리가 일부 겹친다.
- 이로써 Walk 4방향 모두 Idle 상체를 쓴다. 컨셉 Walk 그림은 더 이상 게임 시트에 쓰이지 않는다.

## 재생성과 확인

프로젝트 루트에서 Pillow·numpy·scipy가 설치된 Python으로 다음을 실행한다.

```powershell
python -B Tools/build_e_character_b.py
powershell -NoProfile -ExecutionPolicy Bypass -File .\Tools\Test-E-SpriteAlignment.ps1
```

생성기는 8개 게임 시트와 개별 프레임, 마젠타 시트, 확대 미리보기, Master 파생본을
함께 갱신한다. 기존 `Tools/Export-E-Animations.ps1`과
`Tools/Export-E-MasterSprites.ps1`도 이 생성기를 호출한다. 컨셉 자르기·찐빠 정리·색 복원은
모두 생성기에 들어 있어서 재실행해도 유지된다.

찐빠 정리 이후 컨셉을 새로 자르므로 알파 마스크는 이전 B 시트와 다르다. 수치 검증은 위
"찐빠 정리"의 검증 줄을 따른다. 실제 게임 화면에서의 색감과 애니메이션 체감은 아직 사용자
확인이 필요하다.
